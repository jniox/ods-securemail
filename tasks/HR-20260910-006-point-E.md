# HR-20260910-006 point E — Désarmer le banc de test securemail

- **Service** : securemail — dépôt `~/dev/projects/securemail`
- **Branche** : `feat/securemail-c20260909-1345-lot0`
- **Départ** : `1f411aa` → **Livré** : `4d4669a` (correctif) puis `08bbe03` (mémoire)
- **Date** : 2026-09-10
- **Rôle** : dev

## Objectif

Retirer l'arme, pas seulement refermer la blessure. Les deux ordres SQL du banc de test
désignaient `_sqlx_migrations` **sans schéma**. Comme `ods_common::db::create_pool` pose
`SET search_path TO securemail, public` et que PostgreSQL **écarte silencieusement** un schéma
absent d'un search_path, le chemin effectif retombait sur `{public}` : le 2026-09-09 à 19:05,
le `DELETE` a effacé les versions 1 à 6 du registre **de docstore**, puis securemail est mort
sur `VersionMissing(7)` — 6 tests sur 6, 16 h de gel comptées à tort comme une régression de code.

Le schéma `securemail` a été pré-créé depuis (blessure refermée). Ce lot qualifie les deux
ordres pour que l'isolation soit portée par **le texte de la requête**, donc par le dépôt, et
non plus par un état de base qui ne voyage pas.

## Preuve que l'arme est désarmée

État de la base **avant** la suite (`ods-postgres`, 127.0.0.1:5435, recréée ce jour à 12:26) :

- schémas présents : `docstore`, `public`, `securemail`
- `information_schema` : **aucun** `_sqlx_migrations`, nulle part
- `set search_path to securemail, public; select current_schemas(false)` → `securemail,public`

C'est le cas « premier passage sur base neuve » : le `DELETE` qualifié échoue sur une table
inexistante et l'erreur est avalée par le `.ok()` déjà présent — il échoue **sans dégât** au
lieu de réussir chez le voisin.


pas été approché.

## Note hors périmètre

Deux souvenirs de l'agent étaient rendus faux par cet incident et ont été corrigés dans un
commit séparé (`08bbe03`), sur le modèle du `1f411aa` déjà présent sur cette branche :

1. le port de l'instance partagée était noté 5433 ; `ods-postgres` écoute sur **5435** (vérifié :
   `127.0.0.1:5435->5432/tcp`), et un serveur différent répond sur 5433 — le souvenir n'était pas
   seulement périmé, il était trompeur ;
2. le souvenir prescrivait de contourner `VersionMissing` par une base jetable et présentait le
   registre partagé comme voulu par conception — c'était la description du **bug**. Le contournement
   est devenu le mauvais réflexe (les tests passent sur l'instance partagée en 1,6 s) et tomberait
   de surcroît sous BR-0011.

Le commit du correctif (`4d4669a`) reste strictement à deux lignes.
